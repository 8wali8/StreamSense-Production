# Handoff: console authentication without pasting a token

Written 2026-09-10 for a fresh session that continues this work. **Status:** option 1 below was built the same day on `auth/01-access-link` (`docs/planning/branches/auth-01-access-link.md`), extended into a sign-in page that gates the whole console; option 3 is next and lands on that page. It records what exists, what the problem is, and how to approach it. Read `CLAUDE.md` first for the repository's conventions; this document only adds what a new session cannot derive from the code.

## The problem

The hosted demo at https://streamsense.dev is protected by gateway auth. Today a viewer gets in by opening the browser's developer tools and pasting one line:

```js
localStorage.setItem("streamsense.authToken", "<jwt>"); location.reload();
```

The owner wants viewers, and himself, to reach the console without handling a raw token. The end state on the product roadmap is "Twitch OAuth for streamers" (`docs/planning/redesign/product-direction.md`, backend gap 7, "Later"), where a streamer signs in with Twitch and owns their channel. The immediate need is smaller: a demo shared with a few people.

## What exists today

**Gateway (api-gateway, Java).** `config/GatewayAuthWebFilter` validates an HS256 JWT on every request whose path matches `protected-paths` (`/graphql`, `/api/**`, `/ml/**`); `/actuator/**` and GraphiQL are excluded. Settings live in `config-server/config-repo/api-gateway.yml` under `streamsense.gateway.auth`: `enabled` (env `STREAMSENSE_GATEWAY_AUTH_ENABLED`, on in the production overlay), `required-issuer: streamsense-local`, `required-audience: streamsense-clients`, `hmac-secret` from the `STREAMSENSE_GATEWAY_AUTH_HMAC_SECRET` secret file (at least 32 bytes; `make secrets` writes 64 hex characters; on the VM it is `/opt/streamsense/secrets/STREAMSENSE_GATEWAY_AUTH_HMAC_SECRET`). `config/GatewayAuthStartupCheck` refuses to start with auth on and no usable secret. WebSocket subscriptions (`graphql-transport-ws`) are authenticated by `config/GatewayWebSocketAuthInterceptor` from the connection parameters; an expired token closes the socket with code 4401 `token_expired`. The token itself carries only `sub`, `iss`, `aud`, `iat`, `exp`; there are no roles or scopes, and nothing in the stack distinguishes one bearer from another.

**A second credential type already exists: share tokens.** `graphql/ShareLinkInterceptor` accepts a GraphQL POST carrying `X-StreamSense-Share` instead of a bearer, resolves it to a deal through analytics-service (`/api/analytics/share/{token}`, `DealService.share` mints and stores the token), and allows only the read-only deal and session queries for that deal, without the fee. This is the closest precedent for "a credential that arrives in a URL": the frontend keeps it in session storage (`src/lib/share-token.ts`, captured from `?share=<token>` by `captureShareToken`) and `authHeaders` in `src/lib/auth-token.ts` sends it as the share header when no bearer token is present. `App.tsx` renders a reduced shell for share-token tabs.

**Frontend (React 19, Vite, Apollo 4, react-router).** The bearer token is read from `localStorage` under `streamsense.authToken` (`src/config/env.ts`, `src/lib/auth-token.ts`); `src/lib/api-client.ts` and the Apollo HTTP and WebSocket links (`src/apollo/client.ts`, `buildConnectionParams`) attach it. There is no login page, no token entry field, and no handling of a 401 beyond `describeError` rendering it in each panel. The console is served by nginx inside the frontend container (`frontend/nginx.conf`, security headers and CSP in `frontend/streamsense-headers.conf`: `connect-src 'self' ws: wss:`, `frame-src https://player.twitch.tv`, scripts `'self'` only), behind Caddy on the VM (`tools/deploy/caddy/Caddyfile`), which terminates TLS for `streamsense.dev` and proxies everything to nginx; nginx proxies only `/graphql`, `/api/`, and `POST /ml/segment` to the gateway. Adding a new gateway route reachable from the browser means adding an nginx `location` and, if the route talks to a new upstream, a network-policy rule (`k8s/network/network-policies.yaml`, checked by `tools/k8s/check_network_policies.py` in CI).

**Minting.** `tools/mint-jwt.py` (standard library; secret through the `STREAMSENSE_GATEWAY_AUTH_HMAC_SECRET` environment variable, `--subject`, `--ttl-seconds`). On the VM, `sudo streamsense-deploy token` mints a 30-day token, and every deploy prints one with the sharing instructions (`tools/deploy/deploy.sh`, `print_sharing_instructions`).

**Hosting.** `docs/hosting.md` is the runbook. The VM is `streamsense-demo` in GCP project `project-896ea82f-08b8-4260-a24`, zone `us-central1-a`, address 35.193.171.122; it is stopped between demos (`gcloud compute instances start|stop streamsense-demo --zone us-central1-a`) and redeployed with `sudo streamsense-deploy` after a merge to `main` (CI publishes images to GHCR and moves the `main` tags). Terraform for the VM is under `terraform/` with local state in the owner's checkout. The Twitch settings live in `/etc/streamsense/twitch.env` on the VM.

## Approaches, in order of effort

**1. A link that carries the token (hours).** Mirror the share-token mechanism for the bearer: on load, if the URL fragment holds `#token=<jwt>` (a fragment, not a query string, so it never reaches Caddy's or nginx's access logs and is not sent to the server), store it under `streamsense.authToken`, remove it from the URL with `history.replaceState`, and continue. `streamsense-deploy` then prints a single link, `https://streamsense.dev/#token=...`, instead of a `localStorage.setItem` line. This solves the demo's pain in one frontend change plus a script change: `src/lib/auth-token.ts` (a `captureAuthToken` next to the share-token capture), `App.tsx` or the Apollo bootstrap where `captureShareToken` runs, a test in the MSW style, `tools/deploy/deploy.sh` (`print_sharing_instructions`), `docs/hosting.md`. Also worth adding: a small "Sign out" or "Enter access link" affordance so a viewer with an expired token is not stuck on 401 panels. Security posture is unchanged: whoever has the link has the token.

**2. A gateway-issued session cookie (a day).** Keep the JWT but move it out of the page: a `POST /auth/session` route on the gateway exchanges a bearer (or the token from the link) for an `HttpOnly; Secure; SameSite=Lax` cookie carrying the same JWT, the auth filter accepts the cookie as well as the header, and the WebSocket interceptor reads the cookie from the handshake. The frontend then needs no token storage at all. This is only worth doing on the way to option 3, and it needs a CSRF story for the REST writes under `/api/**` (the console's manual ingest and channel switch).

**3. Twitch OAuth sign-in (two to three days, the roadmap item).** Authorization Code with PKCE on the gateway: `GET /auth/login` redirects to `https://id.twitch.tv/oauth2/authorize` with the app's client id and `redirect_uri=https://streamsense.dev/auth/callback`; `/auth/callback` exchanges the code at `https://id.twitch.tv/oauth2/token`, calls Helix `GET /users` to learn the login, and mints the gateway's own HS256 JWT (same issuer and audience, `sub` = the Twitch login, plus a `login` claim) delivered as in option 2. The registered Twitch application is the same one the Helix poller needs (see the Helix handoff): one client id and secret, in the existing `TWITCH_CLIENT_ID` and `TWITCH_CLIENT_SECRET` secret files, which the gateway would then also mount. Authorization decisions come next: a signed-in streamer sees their own channel by default, the `/ops` page and the manual ingest routes need an operator allow-list (a config list of Twitch logins is enough for a demo). The frontend gets a sign-in button and a signed-in header; `useStreamer()` should default to the signed-in login. Note Twitch requires the redirect URL to be registered exactly and to use HTTPS, which the domain now provides.

Recommendation: do option 1 now, in its own branch, so the demo is shareable by link this week; then option 3 as the real feature, skipping option 2 unless the cookie transport is wanted on its own.

## Conventions and workflow to keep

- Branch per concern, one PR to `main`, note under `docs/planning/branches/` (or `docs/planning/redesign/` if the work is framed as part of that line) with verification and manual checks. The owner merges, or merges by hand when CI is green; Codex reviews on request (`@codex review` comment); the previous rounds fixed P1 findings and recorded P2s in the notes.
- Frontend rules in `CLAUDE.md`: no `fetch` outside `src/lib/api-client.ts`, env reads only in `src/config/env.ts`, errors through `describeError`, tests with a real Apollo client and MSW at the network edge, `npm run codegen:check`, lint, `format:check`, `test:coverage` (floors), `build`. Gateway rules: Spotless (palantir), ArchUnit layering, JaCoCo floors, problem details for errors, every outbound HTTP call bounded.
- Local verification that worked from WSL: Node 20 is installed; the frontend gate runs on a `git clone --shared` of the branch onto the Linux filesystem (`npm ci` there, then the five checks). Java needs Maven 3.9 or later (WSL's 3.8.7 fails the enforcer; a 3.9 tarball from `dlcdn.apache.org` unpacked anywhere works) and JDK 21 (installed). Run one service's tests at a time with small heaps (`MAVEN_OPTS=-Xmx384m`, `-DargLine=-Xmx640m`); the machine has about 3 GB free and parallel builds get killed. Docker Desktop was not running during the last sessions; `docker.exe compose config` still renders without the daemon.
- Git from WSL cannot push (no credentials); commits and pushes go through the Windows git: `"/mnt/c/Program Files/Git/cmd/git.exe" -C 'C:\...\StreamSense-Production' ...` with `-c user.name="Ujjawal Prasad" -c user.email="ujjawalprasad111@gmail.com"`. `gh` is at `~/.local/bin/gh`. - After the merge: start the VM, `sudo streamsense-deploy`, and check https://streamsense.dev from outside; the script verifies the certificate, the redirect, the 401 without a token, and the health query with one.
