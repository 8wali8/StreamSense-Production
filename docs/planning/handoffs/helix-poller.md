# Handoff: turning on the Twitch Helix poller

Written 2026-09-10 for a fresh session that continues this work. It records what exists, what is unknown, and the order to do things in. Read `CLAUDE.md` first for the repository's conventions and `docs/contracts/sessions.md` for the session model; this document adds what a new session cannot derive from the code.

## The problem

analytics-service can poll the Twitch Helix API to learn which watched channels are live, with title, category, and viewer counts, and to turn that into stream sessions with viewer samples; Helix is also what lists a channel's recordings for the VOD import feature on the deal page. All of that shipped in the redesign line (`docs/planning/redesign/02-sessions.md`, `08-vod-import.md`) but has only ever run against MockWebServer in tests: nobody has yet registered a Twitch application, put its credentials on the VM, and watched the poller work against the real API. Without it, sessions are derived from captured events (`CAPTURE` source), viewer counts are absent so the value tiles stay empty, and the "Earlier streams on Twitch" import panel cannot list recordings.

## What exists today

**Code (analytics-service).** `twitch/TwitchHelixClient` (Helix `GET /streams` for the watched logins, `GET /videos` for a channel's archives and a single video; bearer from `twitch/TwitchAppTokenProvider`, which fetches a client-credentials app token from `https://id.twitch.tv/oauth2/token` and refreshes it `token-refresh-margin-seconds` before expiry; a 401 invalidates the token and retries once). `twitch/StreamSessionPoller` runs every `poll-interval-ms` (default 60 s, first run after `initial-delay-ms` 15 s): it builds the watch list from the configured `channels`, every streamer with events in the last `watch-streamers-seen-within-hours` (24), and every streamer with a running deal (`DealService.streamersWithActiveDeals`), asks Helix which are live, records a viewer sample per live stream (`StreamSessionService.recordHelixLive`, source `HELIX`, keyed by Twitch's stream id), and closes the Helix sessions of watched channels that are no longer live. `config/TwitchHelixConfig` creates the client and poller beans only when `streamsense.twitch.helix.enabled` is true, so with the toggle off nothing Helix-related exists in the context and `VodImportService.list` fails with a clear `IllegalStateException`. Tests: `twitch/StreamSessionPollerTest`, `twitch/TwitchHelixClientTest` (MockWebServer), `VodImportTest`.

**Configuration.** `config-server/config-repo/analytics-service.yml`, block `streamsense.twitch.helix`: `enabled` (`STREAMSENSE_TWITCH_HELIX_ENABLED`, default false), `client-id` and `client-secret` (`${TWITCH_CLIENT_ID:}` and `${TWITCH_CLIENT_SECRET:}`, resolved from the secret files through `configtree:/run/secrets/`), `base-url`, `token-url`, `poll-interval-ms`, `initial-delay-ms`, `channels` (`STREAMSENSE_TWITCH_HELIX_CHANNELS`, comma-separated), `watch-streamers-seen-within-hours`. The properties class is `StreamSenseProperties.Helix` (also `connect-timeout-ms` 2000, `read-timeout-ms` 5000, `token-refresh-margin-seconds` 60).

**Secrets.** Two files, `secrets/TWITCH_CLIENT_ID` and `secrets/TWITCH_CLIENT_SECRET`, mounted into analytics-service by `docker-compose.yml` (`secrets:` block). `make secrets` and `tools/start-stack.ps1` create them empty from the committed `.example` files (never random: a random client id would be wrong, and empty keeps polling off). Kubernetes reads the same names from `k8s/secrets/streamsense.env` (`secretKeyRef` in `k8s/apps/analytics-service.yaml`). Egress to Twitch from analytics-service is allowed in `k8s/network/network-policies.yaml`.

**Hosting.** The VM is `streamsense-demo` in GCP project `project-896ea82f-08b8-4260-a24`, zone `us-central1-a`, at https://streamsense.dev (Caddy edge, HTTPS). It is stopped between demos and started with `gcloud compute instances start streamsense-demo --zone us-central1-a`; `sudo streamsense-deploy` on the VM pulls the images CI published for `main` and restarts what changed. The Twitch settings the stack reads come from `/etc/streamsense/twitch.env` (template `tools/deploy/twitch.env.example`; today it holds the chat username and IRC token, the three capture toggles, and `STREAMSENSE_DOMAIN=streamsense.dev`; `STREAMSENSE_TWITCH_HELIX_ENABLED` is absent, so false). The runbook `docs/hosting.md` has a paragraph on writing the two secret files on the VM (`/opt/streamsense/secrets/…`, mode 644 inside the 0700 directory) and turning the toggle on.

**What the console shows.** Sessions and their viewer numbers feed the home page history and track record (`frontend/src/features/home/`), the session report header (`features/session/`), the deal page totals and trend (`features/deals/`), and the "Earlier streams on Twitch" import panel (`features/deals/ImportStreams.tsx`). The `/ops` page shows pipeline status but has no Helix status indicator; the only signals today are the analytics-service log (`helix poll watched=… live=… closed=…` at debug, warnings on failures) and the sessions themselves (`GET /api/analytics/sessions?streamer=<login>`, GraphQL `sessions`).

## What is unknown

Update 2026-09-10: steps 1 to 3 are done. The application was already registered; the VM's secret files were empty and the toggle absent, which is why nothing happened there while the Docker Desktop stack (same credentials in the worktree's `secrets/`) worked. With the files written and `STREAMSENSE_TWITCH_HELIX_ENABLED=true` plus a verification channel in `STREAMSENSE_TWITCH_HELIX_CHANNELS`, `sudo streamsense-deploy` brought up a `HELIX` session with title, category, viewers, and a sample per minute, and the recordings listing returned twenty archives. The app-token flow and the field names of `GET /streams`, `/users`, and `/videos` match the client; the answers carry `Ratelimit-Limit: 800`, `Ratelimit-Remaining`, and `Ratelimit-Reset` (epoch seconds). The 429 handling is `fix/helix-rate-limit` (`docs/planning/branches/helix-rate-limit.md`). Still unknown: the two bullets below.

- What happens to an open `HELIX` session across a VM stop and start, and whether `closeHelixSessionsNotLive` closes it correctly on the first poll after the restart.
- Whether the watched-channel discovery (`streamersSeenSince`) surprises: every login that had events in the last day is polled, including the replay alias `redbull-testing`, which is not a live channel.

## Approach, in order

1. **Register the application.** At https://dev.twitch.tv/console/apps: name it, category "Analytics Tool" or similar, and set an OAuth redirect URL (required by the form; for the client-credentials flow it is never used; `https://streamsense.dev/auth/callback` is a sensible value and is what a later Twitch sign-in would use, see the console-auth handoff). Note the client id and generate a client secret. Keep both out of the repository; they are files under `secrets/`.
2. **Prove it locally first.** With Docker running: write the two values into `secrets/TWITCH_CLIENT_ID` and `secrets/TWITCH_CLIENT_SECRET` in the checkout, start the stack with `STREAMSENSE_TWITCH_HELIX_ENABLED=true STREAMSENSE_TWITCH_HELIX_CHANNELS=<a channel that is live right now> make up` (or `make up-fast`), then watch `docker compose logs -f analytics-service` for the first poll after 15 s and query `GET http://localhost:8080/api/analytics/sessions?streamer=<login>` (through the gateway; auth is off locally) or the GraphQL `sessions` query in GraphiQL. Expect one `HELIX` session with `live: true`, a viewer sample per poll, title and category. Stop the channel from being watched (remove it from `channels` and wait) or wait for it to go offline and confirm the session closes. Then open a deal page for that streamer in the console and confirm the "Earlier streams on Twitch" panel lists recordings; importing one exercises `GET /videos` and the replay path. If Docker is not available locally, skip to step 3 and do the same checks on the VM.
3. **Enable it on the VM.** Start the VM; write the two secret files as the runbook describes; add `STREAMSENSE_TWITCH_HELIX_ENABLED=true` (and optionally `STREAMSENSE_TWITCH_HELIX_CHANNELS=`) to `/etc/streamsense/twitch.env`; `sudo streamsense-deploy` (only analytics-service restarts, since only its environment changed). Verify with the analytics-service log over SSH, then through the console at https://streamsense.dev with the viewer token. Record what was observed in a note under `docs/planning/branches/` or `docs/planning/redesign/` (the redesign README's status section is the running record for this line).
4. **Fix what the real API reveals**, each in its own branch with a test: field mismatches in `TwitchHelixClient` (none found), a 429 back-off (done, `fix/helix-rate-limit`), excluding logins Helix does not know from the watch list (the replay alias returns no user, so polling it is wasted), and the deferred P2 that touches this area ("close reused Helix sessions with the VOD's known end time", `StreamSessionService.recordVod`).
5. **Make it visible.** A Helix status line on the `/ops` page (last poll time, watched count, live count, last error) is a small addition: a `GET /api/analytics/helix/status` on analytics-service exposing the poller's last result, a gateway route, and a pill in `features/ops/`. Optional, but it turns "is it working" from a log grep into a glance.

## Conventions and workflow to keep

- Branch per concern, one PR to `main`, a note with verification and manual checks. Codex reviews on request (`@codex review`); the last round fixed P1s and recorded P2s in `docs/planning/redesign/README.md`.
- Java rules from `CLAUDE.md`: Spotless (palantir), ArchUnit layering, JaCoCo floors per module (never lowered), problem details for REST errors, every outbound HTTP call bounded (the Helix client already sets connect and read timeouts through `RestClient`), a network-policy rule for any new outbound dependency.
- Local Java verification from WSL needs Maven 3.9 or later (WSL's 3.8.7 fails the enforcer; unpack a 3.9 tarball from `dlcdn.apache.org`) and JDK 21 (installed); run one service at a time with small heaps (`MAVEN_OPTS=-Xmx384m`, `-DargLine=-Xmx640m -XX:+UseSerialGC`, `-Dtest=…`), because the machine has about 3 GB free and parallel builds get killed. `mvn spotless:apply` before committing.
- Git from WSL cannot push; use the Windows git (`"/mnt/c/Program Files/Git/cmd/git.exe" -C 'C:\…\StreamSense-Production'`) with `-c user.name="Ujjawal Prasad" -c user.email="ujjawalprasad111@gmail.com"`. `gh` is at `~/.local/bin/gh`.
- Secrets never enter git: the two Twitch files are ignored under `secrets/*`; only the `.example` placeholders are committed. Do not paste the client secret into a PR, a note, or a chat.
- The VM bills while running (about $0.27 per hour); stop it after testing.
